[TEST-06] Missing Rate Limiting

	Status:


	Project:
	ALIKOHUB ACADEMY




Labels:
	Login , Register
	Priority:
	Medium




Description
	There is no mechanism in the api-gateway-service to limit the number of requests originating from a single IP address within a specific timeframe. During testing, it was possible to send 20+ registration attempts and login attempts per second without receiving an HTTP 429 (Too Many Requests) response.








Steps to Reproduce:


1. Prepare Environment: Ensure the API Gateway and Auth Service are active and healthy.
2. Open API Client: Open an API testing tool such as Postman,or any automated REST client.
3. Test Registration Flow:
* Configure a POST request to the registration endpoint.
* Submit a series of 20 unique registration requests in rapid succession (e.g., using a different email each time).
* Observe that every single request returns a 201 "Created" status with no blocking or delay.
4. Test Login Flow:
* Configure a POST request to the login endpoint.
* Submit 20 consecutive login attempts within a few seconds using any credentials (valid or invalid).
* Observe that every attempt returns a standard 200 "OK" or 401 "Unauthorized" status.
5. Verify Global Throttling: Confirm that the server never intervenes with an HTTP 429 "Too Many Requests" response across either endpoint.
Expected Result: The system should detect the abnormal frequency of requests from a single source and temporarily block the client after a set threshold (e.g., 10 requests) to protect against automated brute-force and bot-creation attacks.


Actual Result: The server processes 100% of the traffic without any rate-limiting intervention, allowing an unlimited number of login or registration attempts to be executed programmatically.


























[TEST-07] Unauthorized Access to User Academy Status

	Status:


	Project:
	ALIKOHUB ACADEMY




Component
	api-gateway-service / auth-service
	Priority:
	Medium




Description
	The system fails to validate object ownership when retrieving user-specific academy status records. An authenticated user can bypass authorization logic by manipulating the userId parameter in the URL provided to the 
getUserAcademyStatus
 endpoint. This allows any user to peek at the internal roles, status, and pending application flags of any other user in the database.






Steps to Reproduce:
1. Preparation: Log in as User B (ID: 37) and obtain a valid Bearer Token.

2.     Target Selection: Pick a target user, for example, User A (ID: 3 or 4..5..).
3.     Cross-User Data Request: Send a GET request to User A's status endpoint while using User B's token:    4.   Observe the Vulnerability: The system returns the private academy details for User 25, despite the requester being User 37. The expected behavior should be a 403 Forbidden.


Actual Behavior:
Request: GET /auth/academy/user-status/25 (sent by User 37).
HTTP Status: 200 OK
Response Body: The API returns the full private data belonging to User 25, including their role, enrollment status, and teacher application flags.
Result: FAIL. Private user data is leaked to an unauthorized party.


Expected Behavior:
Request: GET /auth/academy/user-status/25 (sent by User 37).
HTTP Status: 403 Forbidden
Response Body: {"statusCode": 403, "message": "You are not authorized to view another user's academy status", "error": "Forbidden"}
Result: PASS. The data remains private; only User 25 or an Administrator can see it.


Proposed Fix: Update the API Gateway to compare the User ID from the URL with the User ID from the authenticated token. If they don't match (and the user isn't an Admin), the request must be blocked.
      File:  `api-gateway-service/src/auth-service/auth.controller.ts`
      Logic: Use req.user.id to verify ownership of the :userId parameter.










[TEST-08] Critical Privilege Escalation via Teacher Approval Bypass
	Status:


	Project:
	ALIKOHUB ACADEMY




Component:
	api-gateway-service / auth-service
	Priority:
	High




Description
	Unauthorized users can promote themselves (or others) to the INSTRUCTOR role.The administrative endpoint for approving teacher applications lacks role validation. A user with the base USER role can successfully call the approval endpoint for their own or any other user's application.




















1. Login as a standard user to get a JWT.


2. Submit a teacher application via POST /auth/academy/apply-teacher (Status starts as PENDING).


















3. Call POST /auth/academy/approve-teacher/:applicationId using the student's JWT.


4. Relogin or check profile; academyRole has changed from STUDENT to INSTRUCTOR.




Actual Result: The server returns 200 OK with the message: "Teacher application approved and instructor role assigned". The user's role is immediately updated in the database without any administrator review.


Expected Result: The server should return 403 Forbidden. The request should be blocked because the user lacks the ADMIN global role required to manage applications.


Proposed Fix:
1. Gateway Layer (First Line of Defense): Apply the AdminAccessGuard to the vulnerable routes in api-gateway-service/src/auth-service/auth.controller.ts


  @UseGuards(AuthGuard, AdminAccessGuard)
  @Post('academy/approve-teacher/:applicationId')
  async approveTeacher(...) { ... }


2. Microservice Layer (Defense in Depth): Update auth-service/src/auth/auth.service.ts to verify the requester's role before executing the database update.


async approveTeacherApplication(applicationId: string, requestingUserRole: string) {
    if (requestingUserRole !== 'ADMIN') {
        throw new RpcException({
            statusCode: HttpStatus.FORBIDDEN,
            message: 'Only admins can approve applications'
        });
    }
    // ... proceed with update
}
3. Remove Backdoor: Delete the hardcoded mock-id check in the AuthServicethat allows skipping database lookups entirely.
